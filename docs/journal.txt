2026-09-04 — repo created, discovery through scoring working on live data
--------------------------------------------------------------------------
Built from the shape of upwork-agent: poll -> screen -> score, one orchestrator,
pure gates, SQLite for idempotence and for answering "why not" later.

The strategy this serves, from the operator's own measured data: ~50 form
applications produced 1-2 callbacks (~3%); 10 accepted cold LinkedIn messages
produced 4-5 recruiter calls (~50%). Outreach converts 15-20x better than the
form. So the form is a compliance step and the outreach is the application —
and the send stays human, because automating it saves fifteen seconds, moves
the 50% not at all, and risks the account that carries the whole channel.

Sources verified live rather than from documentation:
  ashby       api.ashbyhq.com/posting-api/job-board/bjakcareer   3084 postings
  greenhouse  boards-api.greenhouse.io/v1/boards/skydreams/jobs     4 postings
  lever       api.lever.co/v0/postings/gopuff                    765 postings

Three bugs found by running it, not by reading it:

  1. Dedupe ran BEFORE screening and kept the first occurrence. Bjak lists one
     posting per market, so the Netherlands variant was dropped as a duplicate
     and its Sydney twin was judged: 287 of 291 rejected on location. Moved
     dedupe after screening. The gates are pure, so judging every variant is
     free, and the survivor of a duplicate set is now a role we can take.

  2. The location gate passed any short bare locality as "country unknown",
     meant for Greenhouse writing "Utrecht" without a country. It also passed
     "Kuala Lumpur", which is how 688 of 3088 postings cleared the gates on the
     first run. Inverted: home localities are matched by name, and a location
     the board states but we cannot recognise is a rejection.

  3. maxAgeDays was 14, carried over from Upwork reflex. Both live Skydreams
     roles the operator is actually pursuing are 59 and 86 days old and still
     open — for a permanent role that means they have not found anyone, which
     is information in his favour. Freshness moved to scoring; the gate is now
     120 days and exists only to drop postings a board forgot to close.

Final pass on live data: 3088 seen, 38 kept, 12 duplicate listings dropped.
Both Skydreams Senior PM roles come through at 65.7 and 65.5.

Not built yet: src/enrich/ (hiring-manager resolution when jobPoster is absent,
recent posts for a specific observation) and src/draft/ (the 300-char
connection note grounded in the evidence corpus). Interfaces defined.

2026-09-04 (cont.) — configurable AI layer, and enrich as an MCP agent
------------------------------------------------------------------------
Two things, on Mahi's brief: make the model provider swappable so a local SLM
can be tested against Claude, and build enrichment as a real agent over MCP
rather than a fixed sequence.

Staging already had what was needed: ollama 0.21.0 serving qwen2.5:3b and
llama3.2:3b, plus nomic-embed-text. No GPU, 4 cores, ~3GB free. A structured
extraction test returned schema-valid JSON first try in 23.9s for 19 tokens.

That latency shapes the hypothesis. Extraction is seconds; a 1,500-char letter
is ~400 tokens and would take 8-10 minutes. So the eval must score the
operations separately — "can an SLM replace Claude" has a different answer for
schema-filling than for prose, and one verdict would hide it.

src/ai/ — the model boundary. Three operations, in ascending order of how hard
they are for a small model: parse (schema-constrained), complete (prose), step
(one turn of tool use). Both providers use their own NATIVE constraint
mechanism — Anthropic output_config, Ollama `format` and `tools` — never
JSON.parse over free prose, because the difference between those is the thing
being measured.

Provider is selected PER TASK, not globally (config.ai.tasks). The likely
production answer is a mix, and a global switch would force an all-or-nothing
choice the evidence will not support.

Deliberately NOT using Mastra or LangChain. The loop is 60 lines and there is
no memory to manage — the agent's whole working state is one posting and a
message array, and anything durable is already in SQLite. The decisive reason
is narrower: a framework normalises both providers behind its own adapter, so
the comparison would measure the adapter rather than the models. Reconsider if
this ever grows cooperating agents, durable resumable workflows, or approval
steps mid-loop. None are true.

src/enrich/ — the only agentic surface in the system. "Find who to approach"
genuinely branches: the poster may be the hiring manager, a recruiter, or
absent, and the right next move differs. Everything else stays deterministic
because it runs over thousands of postings and has to stay explainable.

MCP is the transport but the agent does NOT see `call-actor`. Three narrow
tools with fixed actor names and small schemas: letting a model pick an
arbitrary actor is letting it pick an arbitrary bill, and the call-actor schema
alone would swamp a 3B model. Cost per tool is declared and charged before the
call, so the loop refuses rather than overspending.

7 agent-loop tests, all against a scripted model, no network: tool results
reach the next step, budget refuses before billing, a hallucinated tool name is
reported back rather than dropped, a throwing tool does not kill the run, a
looping model is stopped by maxSteps, a model error ends cleanly.

KNOWN GAP, found by dry-running against real data: ATS sources carry neither a
job poster nor a company LinkedIn URL — only the LinkedIn source does. So
`find_people_at_company`, which needs a company URL, is unusable for every
Ashby and Greenhouse posting, which is most of them. Needs a company-name to
LinkedIn-URL resolution step before the agent is useful on ATS-sourced roles.

2026-09-04 (cont.) — goal-directed agent on Mastra, and the SLM comparison
----------------------------------------------------------------------------
Mahi corrected the framing: not a deterministic pipeline with one model call
in it, but an SLM given a GOAL at runtime, reaching Apify through MCP, judging
what comes back, orchestrated by Mastra. Built that.

I had argued against a framework twice on the grounds that it would normalise
both providers behind its own adapter and so measure the adapter rather than
the models. That objection is real but it is answerable by measurement rather
than by argument, and it is his call. Both paths now exist, which turns the
disagreement into an experiment:

  src/enrich/   hand-rolled loop, narrow hand-written tools    (baseline)
  src/agent/    Mastra Agent, full Apify MCP tool surface      (the bet)

The second is materially more ambitious. The agent is not given wrappers I
wrote — it gets Apify's own MCP tools and can search the store, read an
actor's input schema, and run it. Discovering that an actor exists is part of
the job rather than something a developer anticipated.

Stack: @mastra/core 1.64, @mastra/mcp 1.17, ai 7.0.92, ollama-ai-provider-v2
for the local path, @ai-sdk/anthropic for the baseline. Both models reach
Mastra through the Vercel AI SDK, so the orchestrator does not know which is
which — one goal, one tool surface, one orchestrator, model as the only
variable.

src/agent/run.ts records what actually matters for a small model in a loop,
which is not pass/fail:
  - hallucinated tool names (checked against the real MCP tool list)
  - number of tool calls and wall time per run
  - whether the final block came back in the required shape at all
  - whether the observation is GROUNDED: its quoted SOURCE must appear in
    something a tool returned, same rule as everywhere else in this system

`npm run agent -- --compare <job-id>` runs both on identical input and writes
the full trace to data/runs/.

NOT YET RUN. APIFY_TOKEN is unset in this environment, so the Mastra path is
typecheck-clean and completely unexercised. Nothing here should be trusted
until it has run once against both providers.

Known risk worth stating before the first run: the Apify MCP surface is large
and the tool names are namespaced (apify_call-actor and similar). A 3B model
has to reproduce those exactly, and the generic call-actor schema is big. If
qwen fails, tool-name accuracy and schema size are the first things to look at
before concluding the model cannot hold a goal.

2026-09-04 (cont.) — connection scaffolding, and the tool surface as a variable
--------------------------------------------------------------------------------
Mahi asked whether the Mastra orchestrator loads its tool list at runtime. It
does — MCPClient.listTools() is called when the agent is built and nothing is
hardcoded. But checking Apify's docs turned up something that matters more for
the SLM hypothesis than anything else built so far.

The Apify MCP endpoint takes a `tools=` query parameter:

  https://mcp.apify.com/                                        discovery tools
  https://mcp.apify.com/?tools=actors,docs                      tool groups
  https://mcp.apify.com/?tools=harvestapi/linkedin-company,...  named actors

So the tool surface is a variable, not a fixture. The difference for a 3B model
is large: with `discovery` it must run search-actors, then fetch-actor-details,
then call-actor with a generic schema — three round trips at ~30s each, and a
big schema to hold. With `narrow` it calls one named tool with a small typed
schema. If qwen fails, that distinction decides whether the finding is "small
models cannot hold a goal" or "the surface was too big", and those have very
different consequences.

config/connections.json — MCP servers and the credentials they need. The file
is committed to a public repo so it names the ENV VAR, never the value.
Resolution happens at startup; a missing token disables that server with a
warning instead of throwing mid-run. Keys beginning with `$` are documentation
(JSON has no comments) and are stripped before anything iterates — the first
version of the probe crashed because `$comment` was read as a tool profile.

Three tool profiles ship: narrow, discovery, all. `npm run agent -- --tools
discovery` repeats the same goal on a different surface, which is the cheapest
experiment available and should be run before drawing any conclusion about the
model.

npm run connections shows what is wired, what each profile would give the
agent, and — once a token exists — connects and lists the tools the servers
actually expose, so a profile naming an actor that no longer exists fails there
rather than mid-run.

Still not run. APIFY_TOKEN remains unset.

Every finding from the first two runs was a bug in the harness, not the agent.
Recording them because each would have produced a false conclusion:

  1. `--tools narrow <job-id>` parsed "narrow" as the job id. Flag VALUES were
     not excluded from positional arguments. Only shows up when two flags are
     combined.

  2. maxSteps 10 cut Claude off one step from an answer, and the report called
     that "NO USABLE ANSWER". Running out of budget and being unable to answer
     are different findings; conflating them would have understated the
     baseline. Now reported separately (answered / max_steps / no_block /
     error) and the default is 20, because a full enrichment is resolve company
     -> find people -> read posts with a dataset read after each.

  3. Tool calls were counted twice. Mastra exposes each call under `toolCalls`
     as {payload:{toolName,args}} AND flat inside `content`; reading both
     reported 16 calls for 8. `toolCalls` is authoritative.

  4. THE IMPORTANT ONE. toolResults store the payload at `payload.result`, and
     the harness read `r.result` — undefined on every call. The transcript was
     therefore empty and the grounding check reported Claude's observation as
     ungrounded. That is a verifier accusing the model of fabricating when the
     verifier is the thing that is broken, which is the worst way for it to
     fail. It now distinguishes "source not found in tool output" from
     "UNCHECKABLE — no tool output captured", and prints the transcript size
     so an empty one is visible rather than silent.

Claude baseline, once the harness was right: 8 tool calls, ~130s, zero
hallucinated tool names. The sequence was clean — resolve Skydreams, project
the dataset to the fields it wanted, search for product people, refine with

posts. Two things it did unprompted that are worth noting against the SLM
comparison: it used `fields=` projections on every dataset read rather than
pulling whole records, and at one point it said "the dataset already contains
full experience data — let me read it rather than re-run", avoiding a paid
call. Neither was asked for.

2026-09-04 (cont.) — the qwen "failure" was four stacked infrastructure faults
-------------------------------------------------------------------------------
qwen2.5:3b made zero tool calls in 308s and then timed out. That reads as a
capability failure and would have been written up as one. It was not. Four
separate things, none of them the model:

  1. Prompt size. The narrow tool profile is 7 tools at ~5,800 chars of JSON
     schema each = 40,750 chars. Plus system (2,064) and job description
     (3,000), the first request is ~13,090 tokens. Ollama's default num_ctx is
     4,096, and it truncates silently. The model never saw the goal.

  2. OLLAMA_NUM_PARALLEL=4 on the shared daemon. Ollama reserves KV cache per
     parallel slot, so a 16k context reserves four slots' worth — roughly
     9.6GB at f16 on a box with under 4GB free. The model could not have
     loaded at that context no matter how the prompt was sized.

  3. f16 KV cache. At 16k and one slot that is still ~2,416MB, larger than the
     model weights themselves. Quantising the KV cache to q4_0 takes it to
     ~604MB. The KV cache, not the weights, is the binding constraint — which
     inverts the obvious lever: picking a smaller model quant barely helps.

  4. The daemon is shared. /root/whatsscale-ai reaches 11434 from src/agent.ts,
     src/tools/retrieve_knowledge.ts and src/server.ts, and NUM_PARALLEL=4 is a
     deliberate override, not a default. Retuning it for this experiment would
     have serialised another product's inference.

Resolution, Mahi's call between three options: a second Ollama for this repo
alone, on 11435, with its own model store and environment. The shared daemon is
untouched and still serves its four models. ops/ollama-agent.config.cjs runs it
under pm2; ops/README.md records why, and the two things that would silently
reintroduce the failure (pointing baseUrl at 11434, or relying on num_ctx being
passed per request through the AI SDK rather than baked into the model).

Model: unsloth/Qwen3.5-4B-GGUF UD-Q4_K_XL. Unsloth was Mahi's suggestion for
tokens/sec. Two corrections came out of checking it rather than assuming:
Unsloth is not CUDA-only — its docs state NVIDIA, AMD, Intel and CPU with a
Vulkan backend — and its real value here is not speed but a newer, better model
at the same footprint, with Dynamic quants that hold accuracy better per byte.
On a memory-bound box, accuracy per byte is the metric that matters.

`ollama pull hf.co/...` fails repeatedly with "context deadline exceeded"
against HuggingFace on this connection. A direct resumable curl works and is
what ops/README.md documents.

Budget with the isolated instance: ~2,500MB weights + ~604MB KV = ~3.1GB
against ~3,983MB free. It fits, with roughly 880MB of headroom, and that
headroom should be watched during the first long run — an OOM would look
exactly like the model failing, which is the mistake this whole entry is about.

function-vs-prompt-object split IS the deterministic-vs-judged distinction I
had written up as if it were a design insight.

Worse: two of the day's six harness bugs came from parsing Mastra's internals
(payload.toolName, payload.result). Consuming its output rather than reverse-
engineering it would have prevented both. That argues for using more of it.

Deleted: src/enrich/{agent,agent.test,tools,tools.test,enrich,run}.ts — the
hand-rolled loop, its 7 tests, the ToolImpl wrappers and their 6. Tests 42 ->
29, which is the point rather than a regression.

Kept, because no framework gives you this: the four wrapped tools, now as
Mastra createTool. Measured today, gpt-oss-120b on Apify's RAW MCP surface
burned all 20 steps making 18 consecutive searches and never once read a
result — the actor -> datasetId -> get-dataset-items pattern asks the model to
manage an async job lifecycle. On the wrapped tools the same model, same job:

    raw MCP      20 tool calls   224.6s   never read a result
    wrapped       5 tool calls    59.5s   resolve, search, refine, refine

Four times fewer calls, four times faster. A 120B failed on the raw surface, so
a 4B has no chance; fixing the surface is a PREREQUISITE to any local model
working, not a later optimisation.

Grounding moved INTO record_contact. It calls checkGrounding and returns
REFUSED when the citation is absent from the transcript, so a fabricated
observation never commits and the model gets a chance to correct. A committed
result is now grounded by construction, which is strictly better than the
post-hoc scoring it replaces. The spend guard likewise refuses in-band rather
than killing the run.

Harness fault #7, found by this run: the runner labels "searched properly and
honestly found nobody" as `no_block`, i.e. failure — while the prompt
explicitly tells the model not to call record_contact when it finds nobody.
Correct behaviour scored as failure, same class as maxSteps=10 being reported
as "NO USABLE ANSWER" this morning. Needs an `answered_none` outcome, and the
eval set needs that case deliberately: fabricating a contact where none exists
is the worst failure this system has.

UPSTREAM OUTAGE, and the comparison is confounded by it.
harvestapi/linkedin-profile-search returns 0 rows for everyone —
Booking.com included, which has tens of thousands of employees. It worked three
hours ago. Both models were therefore graded against a tool that could not
answer, and BOTH handled it correctly: Claude tried the brand entity Homedeal
as a separate LinkedIn company (genuinely sharp) before reporting honestly;
Cerebras reached the same conclusion in 5 calls to Claude's 9. Neither invented
a person.

Two consequences: a fallback actor is needed
(harvestapi/linkedin-company-employees takes a companies array directly), and
the Sprint 1 §2.3 liveness alarm must cover enrichment tools and not only job
boards. A tool returning empty for EVERYTHING is an outage; without that alarm
it reads as "the agent could not find anyone", which is exactly how this
result would have been mis-written.

the second source automatically. The justification — that the model cannot tell

2026-09-04  Sprint 1 §2.1 + §2.2 — the case set and the scorers

The harness now has both halves it was missing: a set of postings whose right
answer is known, and code that says whether a run got there.

§2.1, the case set. `cases.ts` holds the schema, `prepare-cases.ts` generates a
grading sheet, `check-cases.ts` refuses a set that cannot measure anything —
fewer than two `nobody_findable` cases and nothing ever tests for fabrication;
fewer than two holdout cases and tuning fits the labels and calls it progress.
The sheet deliberately pre-fills no suggested answer. If it did, grading would
collapse into agreeing with the machine, and the set would measure whether the
agent agrees with me rather than whether it is right.

§2.2, the scorers. Four questions, one scorer each, because a single blended
number tells you a run got 0.6 and nothing about which half was wrong:
`answered`, `right_contact`, `no_fabrication`, `grounded`. The last two are
gates — naming somebody who does not exist, or attaching an invented sentence
to somebody who does, is not a worse run, it is the one outcome that reaches a
stranger and cannot be taken back.

Two decisions in there are worth more than the code:

  COMMITTING "NOBODY" IS AN ANSWER. It scores 1 on `answered`, and on a
  `nobody_findable` case it is the correct answer on `right_contact` too. The
  runner used to infer this from free text and label it `no_block`, i.e.
  failure, while the prompt told the model to do exactly that. Same class of
  error as a step ceiling reported as "NO USABLE ANSWER": correct behaviour
  scored as failure.

  AN UNSCOREABLE RUN IS NOT A ZERO. When evidence tools were called and
  returned nothing, `grounded` throws instead of scoring. A blank transcript is
  a broken harness, and scoring a harness fault as a model failure is the single
  mistake that has wasted the most time on this project. It fails loud now.

The trajectory scorer is Mastra's, not ours — `createTrajectoryScorerCode` from
@mastra/evals, which grades expected steps, redundancy, step budget and tool
failures together. This is the scorer that would have caught the largest finding
of the day before without a human reading a trace: on Apify's raw MCP surface a
120B model made eighteen consecutive searches and never read a result. No error,
no answer, nothing a single number would have shown. There is a test for exactly
that shape.

`right_person`, the judged scorer, is built and blind by construction: its
rubric function takes a case and nothing else, so there is no path by which the
judge learns which model produced the answer. A comparison judged by one of its
own contestants flatters that contestant, and the whole point is comparing a
small local model against a large hosted one.

Found while here: `npm test` ran `src/**/*.test.ts` unquoted. The shell expands
that one level deep, so every test file nested two levels down had never run
once. Quoted, the glob goes to Node.

Deviations from the plan's §2.2 table — a new dependency, `right_company`
folded into `right_contact`, `efficiency` dropped — are written up in
sprint-01-plan.md under "What §2.2 actually shipped" and need ratifying.

2026-09-04  v2.0 plan: the model judges, and corrections are recorded

Mahi, after the Skydreams wrong merge: "the user is not expected to fix this
deterministically — the model is supposed to learn this and use its own
judgement." Both halves are right and they are different requirements.
Judgement means the decision moves to a model. Learning means the next decision
is informed by the last correction. v2.0 builds the second first, because
without it the first cannot improve.

I also got two things wrong in the discussion before it, and both are worth
recording because they changed the plan.

  1. I argued against an SLM on cost. That is the weak argument. Our dominant
     cost is Apify at $0.15-0.25 per role, not tokens, and the hardware to host
     a local model is about $17/month against a token bill smaller than that.
     But the strong argument is TRAINABILITY: a model you can train on your own
     corrections encodes your taste permanently, which no hosted model does.
     I attacked the weak case and underweighted the strong one.

  2. I said screening should stay model-free, which was too absolute. Look at
     the rejections: title_wanted threw out 1,976 postings on a regex.
     "Founder's Office Lead" matches no wanted title and might be an excellent
     role. Nobody will ever know, because nobody reads 1,976 rejections. That
     is a false-negative class a model would catch.

     And it points somewhere useful: the best case for a small TRAINED model is
     high-volume, narrow, repetitive judgement where the right answer is
     whatever Mahi would have said — reviewing rejections, not enriching
     contacts. That is the opposite of where an SLM is usually proposed. §2 of
     the plan records it; it is not being built yet.

The plan itself: roleKey becomes a candidate generator, the model decides on
the DESCRIPTIONS rather than the titles — the answer was never in the title,
and jobs.raw has held every description all along, which is the same shape as
reading `headline` from a source that returns `summary`.

Two rules carry most of the weight.

  WHEN UNSURE, SPLIT. The errors are not symmetric. Over-splitting costs $0.14
  twice and shows up as two queue entries. Over-merging is invisible — a job
  never seen, a manager never contacted, no signal ever. You cannot learn from
  an opportunity you did not know existed, so the default favours the error you
  find out about.

  THE JUDGE MUST NOT BREAK THE POLL. It runs unattended. A judge that errors
  falls back to the v1.0 key and the group is re-judged later. Degraded
  grouping is recoverable; a stopped poll is not.

Learning is retrieval, not training: prior corrections for the same company go
into the prompt. Works today, hosted, no GPU. And the same rows are the LoRA or
DPO set if that is ever wanted — every path needs the same artefact, which is
why the corrections table comes first. The system currently records none of
them, so no path is open at all.

regroup and nobody would notice.
